# 时间识别与模型提取约定

时间识别由候选表达提取、统一日历解析、任务语义筛选、模型证据校验与人工审核组成。

## 已支持范围

- 数字和中文数字日期，例如 `2026年十一月八日`。
- 今天、明天、后天、大后天，以及本周、下周、下下周、上周和星期/礼拜写法。
- 天/周相对偏移，例如三天后、两周后。
- 本月/下月的指定日期及月末，处理闰年、跨月、跨年。
- 数字或中文时刻、上午/下午/晚间、半点与刻钟。
- 模糊时间段保留日期精度，例如 `11月8日晚之前` 不会自动变成18:00或23:59。

所有相对日期使用消息原始发送时间，在消息时区内计算。不是服务器当前时间或补采时间。

## 模型兜底

本地 Ollama 与手动导入的 API 使用同一提取提示词。模型输出 `due_text` 原文片段，程序负责日期运算。允许只有日期、不含时刻的证据。

模型选中的原文时间片段通过校验后，既可填 `due_at`，也可填 `due_date`，不覆盖规则已经确定的时间。结果标记 `llm+date` 并保留原文依据。

仍拒绝无原文依据的时间、否定表达、发布时间/上课安排，以及竞争截止日期。学习通结构化截止时间沿用既有的平台优先校验，不用模型覆盖。

当前模型时间补充对正文中多个日期的情况保持保守：规则无法确定且存在多个候选时，继续人工审核，不让模型任选一个。

## 仍需人工处理

农历/节假日、教学周、工作日偏移、重复日程、复杂日期范围和“尽快”等没有明确日历含义的表达不保证解析。未写年份且早于消息发送日的月日表达保留核对，不默认跨年。

通用解析库也不能决定一篇通知中哪个日期属于提交截止。库的默认日期补全和未来偏好不能直接作为业务截止时间。本项目对日历运算和时间精度进行明确控制。参考：[dateparser 文档的相对基准与误识别说明](https://dateparser.readthedocs.io/en/stable/index.html)。

## 验证

增加中文日期、月末、相对日期、时区边界、模型仅日期补充，以及原文、否定、多日期冲突的回归。

本机 qwen3:4b 合成通知冒烟：`请务必赶在本月底把实验报告发过来` 提取 `本月底`，以2026-11-05消息为基准解析为2026-11-30，不补时刻。单条请求约10.49秒，仅为功能验证，不代表性能或准确率基准。

多日期合成通知冒烟：`11月8日晚之前提交期末大作业。明天11月5日上课汇报。`，本机模型返回 `11月8日晚之前`。

本轮完整后端回归：650项通过，4项Windows专属测试跳过。
