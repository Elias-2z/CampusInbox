# CampusInbox 开发进度与后续计划

更新时间：2026-10-31。本文记录当前已交付能力和后续方向；规划项不代表已经可用，也不承诺第三方平台接入一定可行。

项目目标：让分散的校园信息，自动变成可执行任务。当前定位是本机单用户 Web 应用，核心流程已可运行，正在完善可靠性和普通用户的使用体验，尚未达到完整产品的正式发布验收标准。不采用缺少统一验收口径的总体完成百分比。

## 状态说明

- **已实现**：已有可运行代码及对应验证；限制见各项说明。
- **部分实现**：已有基础能力，但尚未覆盖完整目标。
- **待实现**：当前没有可用的完整功能，需后续开发和验收。

### 统一接入流程

计划采用：**Connector 获取数据 → 标准化原始消息 → 去重并保存 → 规则／模型识别 → 收件箱审核 → 确定性业务服务修改任务**。

- 统一 Connector 接口与消息格式，隔离不同平台的授权、拉取和错误处理；结构化作业字段优先直接使用。
- 每个连接展示：授权状态、同步健康状态、监控范围、上次成功同步时间、最近失败原因；账号在线不能等同于同步正常。
- 提供连接／重新授权、断开连接、手动同步、范围选择；支持时增加定期同步、临时错误退避重试、游标与断线补拉。
- 外部消息使用来源标识去重；同步重试或服务重启不能重复创建消息和任务。
- 会话与凭据仅保存在本地适当的安全存储中，不进入仓库、日志或普通导出；普通用户无需手动复制 Cookie。
- 接入失败不能影响粘贴导入与任务管理；不同来源仍复用相同的审核、版本校验、来源记录和撤销流程。

### 平台实施顺序

1. **先做框架与测试数据源**：验证统一消息格式、去重、失败重试和同步状态；不虚构已经连接真实账号。
2. **再评估学习通接入**：优先验证可用授权方式、结构化作业／考试／通知数据和会话有效性，再做端到端同步。
3. **QQ 与微信先做可行性验证**：验证用户账号与指定群范围、平台规则、兼容性和账号风险；不可行时保留复制、转发或截图导入路径。

以上是开发优先级，不承诺平台提供长期稳定的接入方式或永久在线。验收至少覆盖：首次授权、范围选择、一次同步、重复同步、会话过期、网络中断恢复、断开连接和不影响核心应用。

## 推荐开发顺序

| 顺序 | 交付目标 | 完成标准 |
| --- | --- | --- |
| 1 | 数据备份恢复与迁移基础 | 用户可在设置页备份、验证并恢复；失败不破坏现有数据 |
| 2 | 核心理解与冲突流程补齐 | 用固定测试集覆盖复杂变更、多任务与冲突；预览、确认、来源与撤销完整 |
| 3 | OCR 和真实模型评测 | 截图能进入同一审核链路；公布可复现效果及已知边界 |
| 4 | 设置页 Connector 框架与首个可行平台 | 通过测试源和真实平台验收，再按可行性扩展其他连接 |
| 5 | 云端模型、自动化等级、后台提醒 | 明确用户选择、数据流向和失败处理；新增自动行为可验证、可追溯 |
| 6 | 普通用户安装与正式发布 | 完成独立机器验收、许可证与安装说明；安装包按平台分别验证 |

每个阶段保持小步交付，更新本文及对应功能文档。新增 Connector 不绕过核心审核流程，平台接入进展以实际验收为准。
