# 取消通知审核

## 用户流程

先创建原任务，再导入“数据库原理：实验四报告取消，不用再提交。”。收件箱显示可能关联的任务；可以手动选择其他待办或进行中的任务。存在多个候选时不默认选择。点击“预览取消结果”，核对课程、名称、截止时间和状态前后变化，再点击“确认取消这项任务”。

确认只将状态改为 cancelled，不删除任务，不改截止时间、标题或提交要求。通知标记为已处理，详情展示创建来源、取消来源和修改历史。刷新或重启后仍可撤销本次取消，恢复取消前的 todo / in_progress 状态。撤销后通知仍为已处理，旧确认不会再次取消任务。

取消后存在任何后续编辑时，直接撤销返回 409，避免覆盖新内容。可查看历史并人工编辑。手动编辑或恢复状态不会把旧取消记录标记为已撤销；历史会保留实际发生的各次操作。

## 保守识别范围

规则仅支持明确的单任务取消 / 作废 / 无需提交，要求包含可识别的任务名称。没有明确截止时间不产生补充时间警告，也不需要调用模型。问句、条件句、传闻、否定取消、取消延期、部分提交要求变化，以及多个任务或混合变更转人工核对。较复杂的自然语言可能无法进入取消预览，需要人工处理。

后端重新检查原文是否支持此操作，不允许仅修改请求参数把其他通知强制当成取消。只能处理 pending + review 的建议，以及 todo / in_progress 的任务。候选匹配仅供参考，最终目标由用户确认。

## 数据与事务

新增 CancellationProposal / CancellationChange 独立表，使用 create_all 增量初始化，不改变已有表结构。预览固定任务版本、原状态和建议修订时间；确认时全部重新核对。任务状态更新、cancel 事件、通知处理状态、取消关联在同一写事务提交。

一条取消建议只能应用一次；同一预览重复确认返回同一结果，另一个预览返回 409。撤销采用 cancel_undo 新事件，检查 applied_version，记录 undo_event_id；重复撤销不重复修改任务。来源使用本次取消通知的 message_id，原任务最初来源不改变。

任务版本持续递增：预览后即使编辑再恢复，也不能继续使用旧预览。截止时间更新和取消共用任务版本，因此不能互相静默覆盖；旧撤销也不会因另一项操作被撤销而重新变得有效。

## API

- POST /api/suggestions/{id}/cancellation-preview：请求 task_id；返回预览 ID、固定任务快照、proposed_status 和创建时间。
- POST /api/cancellation-proposals/{id}/confirm：返回任务、事件、应用版本和撤销状态。
- POST /api/cancellation-changes/{suggestion_id}/undo：返回撤销后的当前任务和状态。
- InboxItem 增加 cancellation_supported / cancellation_change；TaskDetail 增加 cancellation_changes。取消关联后的 task_id 指向原任务。

尚未实现自动取消、批量取消、取消建议重做、任务合并或多任务自动拆分。
