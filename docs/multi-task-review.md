# 多任务拆分审核

## 范围与用法

支持一条通知中从 1 开始连续编号的 2–20 个条目。每项单独起一行，编号可用 1. / 1、 / 1． / （1） / (1)。当前按明确编号和规则拆分，不调用单任务提取模型，也不承诺理解未编号长段落。

示例：

```text
软件工程：
1. 下周一晚上八点前提交需求分析报告。
2. 下周三下午六点前提交原型设计，上传至学习通。
```

导入后点击“生成拆分草稿”。原文保留一份，草稿显示各自的原文片段、字段、依据和警告。可以分别编辑、保存草稿、确认创建或跳过；跳过项可恢复。只有确认创建的条目才产生正式任务。

一部分已确认时，整条通知仍为待处理；全部确认 / 跳过后，有任务则为已处理，全部跳过则为已忽略。进度、已保存草稿和确认记录均可跨刷新 / 重启恢复。未点击保存的输入只在当前页面保留。

每项时间独立按原消息发送时间与时区解析，缺少具体时刻则留空。只继承编号前明确且唯一的公共课程，不把一项的时间或平台复制给另一项。公共提交要求、尾部统一说明以及跨条目引用需要人工核对和补充。每项涉及取消、延期或非任务内容时不能强制按新任务确认；请另行导入处理或跳过。

## 数据与升级

新增 SplitDraft 表：关联原建议，位置、原文片段、状态、可否创建、字段、依据、警告、关联任务与修订时间。多项任务的 message_id 和 suggestion_id 都指向同一原始 Message / Suggestion；不会复制原始消息，TaskEvent 也记录同一来源。详情使用对应草稿的审核依据，后续编辑和截止时间变更继续按任务独立追踪。

Task.suggestion_id 从唯一索引改为普通索引，让一个建议可以创建多个任务。启动时只迁移已知的旧 ix_task_suggestion_id 唯一索引：先用 SQLite backup API 创建一致性备份，再在事务内替换索引，不重建表、不删除记录。备份位于当前数据库同级 backups/，文件权限 600；正式默认路径为 backend/data/backups/。重复启动不会重复迁移或备份。仍不支持任意旧字段结构的通用迁移。

普通单任务确认仍在写事务中检查建议状态，保持幂等；拆分草稿则用 task_id 和自身状态防止重复创建。重复生成返回相同草稿；已生成后禁止整条重新识别 / 忽略，以免丢失处理进度。改为逐项编辑或跳过。

保存和确认携带 expected_updated_at；旧修订返回 409。确认时重新检查已有相似任务，必要时须明确勾选创建独立任务。确认、任务、创建事件、草稿状态和整体处理进度在同一事务提交。并发确认同一草稿返回同一个任务；已确认项即使编辑了正式任务，再次确认也不会覆盖正式任务。

## API

- POST /api/suggestions/{id}/split：生成或返回拆分草稿与整体 InboxItem。
- PATCH /api/split-drafts/{id}：完整 TaskFields + expected_updated_at；仅保存草稿，不创建任务。
- POST /api/split-drafts/{id}/accept：完整 TaskFields + expected_updated_at + allow_duplicate；返回 TaskRead。
- POST /api/split-drafts/{id}/ignore 或 reopen：expected_updated_at；返回 InboxItem。
- InboxItem 新增 split_supported 和 split_items；多任务的 task_id 留空，逐项任务链接在 split_items[].task_id 中。

尚未实现未编号文本自动拆分、模型辅助拆分、批量确认、任务合并、一个编号中多个任务的再次拆分，以及拆分条目直接应用更新 / 取消。
