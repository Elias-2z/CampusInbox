# 重复通知关联与字段合并

## 用户流程与范围

新任务通知与已有任务相似时，收件箱优先展示“关联已有任务”方式。用户可从候选或其他待办 / 进行中的任务中选择；多个候选不默认选择。仍可切换“创建独立任务”，经过现有重复确认后另建任务。

关联不会默认覆盖任何字段。可以只关联来源，也可以逐项勾选采用通知中的标题、课程、类型、任务内容、截止时间、提交平台 / 方式、文件要求、地点或备注。状态不属于可合并字段。空字段不能清空原任务；日期以相同时间点比较，不把时区格式差异当作冲突。

预览展示固定任务版本、每个勾选字段的原值和确认后值，以及截止时间冲突 / 不同课程 / 历史通知提示。必须明确确认后才更新任务，原任务数量不增加，创建来源不变，新增通知进入来源与历史。没有勾选字段时只记录通知关联；版本仍递增以防旧操作覆盖。

普通通知和多任务拆分的独立草稿均可使用。拆分条目使用已保存的字段；如需修改，先切回创建方式编辑并保存。一个条目可关联已有任务，其他条目继续创建或跳过，整体进度计为“已确认”。同一原文的多个条目可以分别关联同一任务，不复制原文，也不会改变该任务的最初创建依据。

本阶段处理“新通知 / 草稿 → 已有任务”的关联和字段补充，不把两个已创建的任务合并成一个，不支持自动判断冲突胜者。取消 / 延期通知继续使用各自审核流程，整条多任务通知须先拆开处理。需要进一步编辑时，可先只关联，再在任务详情手动编辑。

## 持久撤销与版本冲突

确认后详情、收件箱或对应拆分条目提供撤销入口。刷新 / 重启后仍可撤销，恢复本次实际修改的字段和原字段依据。只关联来源的撤销不会改变业务字段。

撤销记录为 merge_undo 新事件；原文、历史来源与确认记录仍保留，可看到这次关联已撤销。建议 / 条目维持已处理，旧确认重放不会再次执行，也不能借此重复创建。重做或改建独立任务需要人工新建 / 编辑。

预览后任务或源建议 / 草稿被编辑时，确认返回 409；关联后任何后续操作都阻止直接撤销，避免覆盖新信息。字段补充、手动编辑、截止时间更新和取消共用任务版本；即使后续操作撤销，也不会让旧撤销重新有效。

## 数据与事务

新增 MergeProposal / MergeChange 独立表，不修改已有字段与索引。升级前保留本地 SQLite 一致性备份；create_all 增量初始化。

MergeProposal 固定来源 key、建议与可选拆分条目、源修订、目标任务与版本、实际变更前后字段和依据。MergeChange 对来源 key 唯一，记录目标任务、预览、事件、应用版本与撤销事件。一个来源只能应用一次；不同预览不能应用到另一任务。同一预览重复确认和重复撤销均幂等。

拆分条目关联现有任务时不写 SplitDraft.task_id（该字段仍用于创建关联）；由 MergeChange 保存关联，API 返回对应任务链接。这样不会破坏 SplitDraft.task_id 的唯一约束，也不会把关联草稿误用为任务最初的字段依据。

确认以写事务同时更新任务、事件、来源处理状态和关联记录；拆分通知整体进度也在同一事务更新。详情按任务版本回放字段依据，合并采用对应来源依据，撤销恢复此前依据；后续截止时间操作可继续追溯。

## API

- POST /api/suggestions/{id}/merge-preview：task_id + fields（默认空列表）。
- POST /api/split-drafts/{id}/merge-preview：同上，使用已保存草稿。
- POST /api/merge-proposals/{id}/confirm：确认预览。
- POST /api/merge-changes/{id}/undo：撤销本次关联与补充。
- InboxItem 和 SplitDraftRead 新增 merge_change；TaskDetail 新增 merge_changes。关联后的 task_id 返回原任务 ID。

预览响应含 task、before_fields、after_fields、warnings；客户端更换目标或勾选字段后会清除旧预览。服务器独立检查来源类型、状态、修订与目标版本，不接受任意字段名或直接提交覆盖值。
